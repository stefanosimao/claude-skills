**Decision 30 (2026-07-28):** vendor scope is a **per-skill decision recorded in this ledger**, not a blanket rule. "Vendor = repo-only" was a context-budget precaution; the budget is now measured (~3.3k resting for 13 skills, 0.3%) and comfortable. teach · handoff · grilling · grill-me · resolving-merge-conflicts · diagnosing-bugs are promoted to personal CC scope — standalone per their audits and useful outside a codebase. **Decision 31 (mirrored from the Hub, 2026-08-04):** `install-vendor.sh` is **the** vendor distribution path — whole-set only, sha256 pin-verified in **both** directions, with a partial-guard, and a `--private` mode that installs git-excluded and laptop-only. **`--private` and cloud sessions are mutually exclusive**, and not by policy but by mechanism: cloud sessions load only skills *committed* to `.claude/skills/`, so a deliberately git-excluded skill is invisible there. Nothing to reconcile — the two modes address different surfaces.

**Decision 32 (mirrored from the Hub, 2026-08-04; per-machine framing 2026-08-04):** `git-guardrails` installs as a **global `PreToolUse` hook, not a resident skill**. A guardrail that depends on the model choosing to invoke it is not a guardrail; the hook fires on the tool call whether or not any skill is loaded, and costs zero resting context. **Installation is per-machine and does not travel with the repo** — hooks live in `~/.claude/`, which `sync.sh` never writes to, so a fresh clone brings no guardrail. Procedure: **[`docs/new-machine-setup.md`](docs/new-machine-setup.md) step 4**, which also covers verification (registration grep + a live blocked `reset --hard` on a confirmed-clean tree). *This ledger records the design, not which machines have run it* — machine state is checked by running the runbook, never tracked as a checkbox here, because a checkbox rots and blocks unrelated work while a procedure does neither.

*Corollary, since it is easy to miss: the same applies to any later edit of the pattern list. There is **no single source of truth for the hook across machines** — changing it on one leaves the others silently divergent.*

**Coverage boundary, measured rather than assumed (2026-08-04):** the nine patterns match as substrings anywhere in the command, and **seven carry a literal `git ` prefix while only `reset --hard` and `push --force` stand alone.** Consequence: `git -C /other/repo reset --hard` is caught (standalone pattern), but `git -C /other/repo push|clean -fd|clean -f|branch -D|checkout .|restore .` **all get through**, because the `-C <path>` form breaks the `git `-adjacency the other seven depend on. `cd /other && git push` is still caught. **The guardrail is a brake on the command you would type by habit, not a containment boundary** — it stops the accident, not an adversary. Recorded because the bypass was first found by generalizing from a single lucky sample (`reset --hard`, one of the two standalone patterns) to "the `-C` form doesn't slip past", which is false for **six of the seven**. *(Number corrected 2026-08-04 from "five of the seven", and the correction is the same class of error as the original: the first count was read off an enumeration that had silently dropped `git clean -f`, so the prose miscounted its own list. Re-established by executing the hook against all nine patterns in both forms rather than by re-reading it — only `git reset --hard` survives the `-C` rewrite, and it survives because `reset --hard` also stands alone.)* Nothing to fix: the bluntness is the point, and its price is false positives — a `grep` whose *search string* contains `git push` is blocked, which this very paragraph guarantees will happen against this file.

**Decision 33 (mirrored from the Hub, 2026-08-04):** the **enabled-where column records reality.** `sync.sh` stays dumb — it syncs all of `skills/` and never reads this catalog — so the column describes where a skill *works*, never where it is *permitted*. Its discipline applies force only under context-budget pressure. **"claude.ai-primary" is a usage note** (where you actually reach for a skill), **not a restriction**; bonsai-care, settimana-enigmistica and swiss-voting are `CC ☑ + ai ☑` accordingly. Corollary already exercised by yt-gemini: where a row's reach is genuinely narrower than the column implies, it says so inline (`CC ☑ (local only)`) rather than letting the tick overstate it.

**Decision 34 (2026-08-04): this repo is the single source of truth. Nothing else holds an authoritative copy of anything.** Every prose doc lives in `docs/`; Google Drive keeps only the Skill-Library itself — books, `_summaries/`, `_sources.md` — which is its actual job. **One derived copy is permitted, and only because a mechanism requires it:** the repo is private, so a claude.ai session cannot fetch it, and a Skills Hub project with no inventory is a design studio blind to what it has already built. That mirror is **exactly three files** — `catalog.md`, `README.md`, the Hub plan — each carrying the commit it was generated from and **stale unless re-exported**. Procedure: [`docs/mirror-export.md`](docs/mirror-export.md); trigger is the same "catalog.md changed" that fires the `ask-tete` snapshot regen, and `skill-forge` step 6 names the two together so neither is remembered alone. **The distinction that makes this safe is subordination, not location:** a copy with a stamp is a photograph and a reader can date it; a copy without one is a rival, and the reader cannot tell which is current. The three retired Drive copies (`03-catalog.md` 2026-07-29, `catalog.md` + `README.md` 2026-08-04) were all rivals — each plausible, each answering confidently from a state nobody could name. **Secrets go to neither home:** they live in `~/.zshenv` only, and the repo being private does not make it a place for credentials.

## Tools & bridges

*Capability bridges — skills that hand a job to something outside Claude because Claude cannot do it natively. Surface-constrained by construction: they depend on network egress and credentials, so they do not travel to every surface the way a pure-method skill does.*

*⚠️ **Group of one, provisionally.** The group earns its own heading because a bridge is a different species from a method skill — different failure modes (credentials, egress, another model's availability), different attribution rule (the answer is the other model's, not Claude's). If it is still a group of one when the next few skills land, fold `yt-gemini` into Personal and drop the heading — a taxonomy with a singleton category is describing one skill, not a kind.*
